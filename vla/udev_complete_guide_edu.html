1탄생 비화: 세 번의 시대 교체

udev는 어느 날 갑자기 나타난 게 아닙니다. 두 번의 실패를 거쳐 2003년에 완성된 해답입니다.

🏘️
이해하기 쉽게!

옛날 시골 마을은 집이 몇 채 없어서 "첫 번째 집, 두 번째 집"이라 불러도 됐어요. 그런데 도시가 되면서 집이 생겼다 없어졌다 하니, 순서로 부르면 매번 주소가 바뀌죠. 그래서 집마다 고유한 도로명 주소(시리얼 번호)를 붙여주는 주소 관리소가 생긴 거예요. 그게 udev입니다.

💡 실제로는 — "순서 기반 이름(ttyACM0, ttyACM1)"의 혼란을 "신원 기반 이름(by-id)"으로 바꾼 것이 udev의 존재 이유입니다.

제1시대 · 1970~90년대 — 정적(static) /dev
장치는 하드디스크, 프린터처럼 고정되어 있다고 가정했습니다. 그래서 /dev 폴더에 있을 법한 장치 파일 수천 개를 미리 전부 만들어 뒀어요.
😫 문제: 실제로 없는 장치 파일까지 잔뜩 존재. 새 장치를 사면 관리자가 mknod 명령으로 수동 등록해야 했습니다.
제2시대 · 1990년대 말 — devfs의 도전과 실패
"커널이 직접 /dev를 동적으로 만들자!"라는 devfs가 등장했지만, 이름 정책이 커널 안에 고정되어 사용자가 이름 규칙을 바꿀 수 없었고, 경쟁 상태(race condition) 버그도 많았습니다.
📌 교훈: "장치 감지는 커널이, 이름 짓기 정책은 사용자 공간이" 맡아야 한다는 설계 원칙이 여기서 나왔습니다. (udev의 u = userspace가 이 교훈의 흔적!)
전환점 · 2000년대 초 — USB 핫플러그 시대 💥
USB가 대중화되며 장치가 컴퓨터가 켜진 채로 꽂혔다 빠지는 시대가 왔습니다. 꽂는 순서에 따라 이름이 뒤바뀌는(ttyACM0 ↔ ttyACM1) 혼란이 폭발했죠. 기존 방식으로는 감당이 불가능했습니다.
제3시대 · 2003년 — udev 탄생 (커널 2.6과 함께)
커널 개발자 Greg Kroah-Hartman 등이 만든 udev가 devfs를 대체합니다. 커널이 uevent("장치 꽂혔어요!" 방송)를 보내면, 사용자 공간의 udev가 규칙(rules) 파일을 읽어 이름·권한·심볼릭 링크를 부여하는 구조입니다.
🔭 이후: 2012년 systemd 프로젝트에 합류해 현재는 systemd-udevd라는 이름의 서비스로 모든 리눅스에서 돌아가고 있습니다. (우분투 24.04, 라즈베리파이 OS 모두 동일)
📛

udev = userspace + /dev

"/dev를 사용자 공간에서 관리한다"는 설계 철학이 이름에 그대로 담겨 있습니다.

⚖️

역할 분담이 핵심

감지는 커널, 이름 정책은 udev. devfs 실패에서 배운 교훈입니다.

🔥

핫플러그가 낳은 자식

USB 시대의 "순서 혼란"이 없었다면 udev도 필요 없었을 것입니다.

2커널의 조직도: 왜 그룹이 나누어지는가

v4l, tty, input… 암호 같은 이름들은 사실 커널이라는 회사의 부서명(서브시스템)입니다. 장치의 성격에 따라 담당 부서가 나뉘고, 부서마다 전용 폴더와 전용 그룹이 생깁니다.

🏢
이해하기 쉽게!

큰 회사에 신입사원이 들어오면 인사팀이 직무에 따라 부서를 배정하죠. 영상 다루면 영상팀, 통신 다루면 통신팀. 리눅스 커널도 똑같아요. 새 장치가 꽂히면 드라이버가 "이 장치의 직무"를 보고 서브시스템(부서)에 배정합니다. 부서가 정해지면 사무실 위치(/dev 경로)와 출입 권한(그룹)도 자동으로 따라옵니다.

💡 실제로는 — udev rule의 첫 조건이 항상 SUBSYSTEM=="tty"처럼 부서 확인으로 시작하는 이유입니다.

왜 그룹이 부서별로 나누어질까요? 부서마다 위험의 성격이 다르기 때문입니다. 시리얼 포트(dialout)는 로봇 오작동 위험, 카메라(video)는 사생활 침해 위험, 저장장치(disk)는 데이터 파괴 위험 — "카메라를 쓸 수 있는 사람"과 "모터를 움직일 수 있는 사람"을 따로 관리하는 것이 최소 권한 원칙에 맞습니다. 열쇠 꾸러미를 통째로 주지 않고, 방마다 열쇠를 따로 주는 것이죠.

3by-id: 절대 바뀌지 않는 이름의 비밀

udev가 매일 하는 가장 중요한 일 — 순서 기반 이름 옆에 신원 기반 별명(심볼릭 링크)을 세워두는 것.

🪪
이해하기 쉽게!

/dev/ttyACM0은 이사 갈 때마다 바뀌는 집 주소이고, /dev/serial/by-id/...는 절대 안 바뀌는 주민등록번호예요. by-id 폴더는 "주민번호 명부"이고, 화살표(->)는 "이 주민번호의 현재 거주지는 여기"라는 뜻입니다.

💡 실제로는 — by-id 이름은 제조사 + 제품명 + 시리얼 번호를 조합해 만들어지며, 우분투에 기본 내장된 udev 규칙(60-serial.rules 등)이 자동 생성합니다. 우리가 설정하지 않아도 이미 작동 중이에요!

탐색

시스템의 모든 by-id 폴더 찾기

ls -d /dev/*/by-id /dev/*/*/by-id 2>/dev/null
/dev/serial/by-id    ← 시리얼 (모터보드·GPS·LiDAR·IMU)
/dev/v4l/by-id       ← 카메라
/dev/disk/by-id      ← 저장장치
/dev/input/by-id     ← 키보드·마우스·조이스틱
해석

화살표 읽는 법 + 역방향 조회

ls -l /dev/serial/by-id/
usb-1a86_USB_Serial-if00 -> ../../ttyACM0
#  ↑ 고유 이름 (안 바뀜)          ↑ 실제 장치 (바뀔 수 있음)

# 반대로, ttyACM0의 by-id 이름이 뭔지 조회
udevadm info -q symlink --name=/dev/ttyACM0

# 규칙 만들 때 쓰는 만능 조회 (모든 속성 출력)
udevadm info --name=/dev/ttyACM0 --attribute-walk | less
⚠️
코드에서는 by-id 경로를 직접 써도 됩니다! serial.Serial("/dev/serial/by-id/usb-1a86_...-if00")처럼 열면 udev rule을 따로 안 만들어도 순서 문제에서 해방됩니다. rule을 만드는 이유는 /dev/robot_wheels처럼 짧고 의미 있는 이름을 원할 때입니다.

4udev 규칙 해부: robot_wheels 만들기

규칙(rule) 한 줄은 "조건, 조건 → 행동" 구조입니다. LeKiwi 듀얼 보드 실전 예제로 해부해 봅시다.

SUBSYSTEM=="tty", ATTRS{serial}=="67890DEF", SYMLINK+="robot_wheels"
조건 1 — 부서 확인 (==) "tty 부서(시리얼) 소속인가?"
==는 비교를 뜻해요.
조건 2 — 신원 확인 (==) "시리얼 번호가 67890DEF인가?"
이 두 조건을 모두 만족해야 행동 실행.
행동 — 별명 추가 (+=) "/dev/robot_wheels 링크를 추가하라"
+=는 기존 이름을 유지하며 덧붙임.

🛠️ 적용 4단계 (LeKiwi 듀얼 보드)

STEP 1

각 보드의 시리얼 번호 알아내기

udevadm info --name=/dev/ttyACM0 | grep SERIAL_SHORT
E: ID_SERIAL_SHORT=12345ABC   ← 팔 보드
udevadm info --name=/dev/ttyACM1 | grep SERIAL_SHORT
E: ID_SERIAL_SHORT=67890DEF   ← 바퀴 보드
STEP 2

규칙 파일 작성

99-는 우선순위입니다. 숫자가 클수록 늦게 실행되어 기본 규칙을 덮어씁니다.

sudo nano /etc/udev/rules.d/99-lekiwi.rules

# 파일 내용:
SUBSYSTEM=="tty", ATTRS{serial}=="12345ABC", SYMLINK+="robot_arm"
SUBSYSTEM=="tty", ATTRS{serial}=="67890DEF", SYMLINK+="robot_wheels"
STEP 3

규칙 재로드 + 즉시 적용

sudo udevadm control --reload-rules
sudo udevadm trigger
STEP 4

확인 후 코드에서 사용

ls -l /dev/robot_wheels
/dev/robot_wheels -> ttyACM1   ← 성공!
# Python — USB 순서가 바뀌어도 항상 바퀴!
robot_wheels = Robot(port="/dev/robot_wheels")

값싼 CH340 변환칩은 시리얼 번호가 아예 없는 경우가 많습니다. 같은 칩을 쓰는 IMU 2개를 꽂으면 시리얼 번호로는 구분 불가! 이럴 땐 물리적 USB 포트 위치(KERNELS)로 구분합니다: 

# "왼쪽 위 USB 포트에 꽂힌 것이 IMU다"라는 규칙
SUBSYSTEM=="tty", KERNELS=="1-1.2", SYMLINK+="imu"
# 포트 위치 값은 udevadm info --attribute-walk에서 확인

단, 이 방식은 "항상 같은 포트에 꽂아야 한다"는 약속이 필요합니다. 교육 현장에서는 포트에 라벨 스티커를 붙여두는 것이 실전 노하우!

p3PCI bus 3 — 메인보드에서 꽂힌 버스 번호
s0slot 0 — 슬롯 번호

옛 이름 eth0/eth1은 부팅 때 먼저 인식된 순서였지만, enp3s0은 메인보드의 물리적 위치입니다. 아파트 "301호"가 입주 순서와 무관하듯, 위치는 부팅 순서와 무관해 절대 바뀌지 않죠. 덕분에 netplan 설정과 FastDDS 인터페이스 화이트리스트에 이름을 안심하고 박아둘 수 있습니다.

🔬 사례 심화 ②: 라즈베리파이 GPIO 권한 규칙

내장 규칙

라즈베리파이 OS의 99-com.rules 핵심

# "GPIO 장치가 나타나면 → 그룹 gpio, 권한 rw-rw로 바꿔라"
SUBSYSTEM=="gpiomem", GROUP="gpio", MODE="0660"
SUBSYSTEM=="i2c-dev", GROUP="i2c",  MODE="0660"
SUBSYSTEM=="spidev",  GROUP="spi",  MODE="0660"

# 사용자는 명단에만 오르면 끝 (dialout과 같은 패턴!)
sudo usermod -aG gpio,i2c,spi $USER
🚨
RPi5 + Ubuntu 24.04 주의: 이 규칙과 그룹은 라즈베리파이 OS의 것이라 우분투에는 기본으로 없을 수 있습니다. 직접 추가하세요: 
sudo groupadd -f gpio
sudo usermod -aG gpio $USER
echo 'SUBSYSTEM=="gpio*", GROUP="gpio", MODE="0660"' | sudo tee /etc/udev/rules.d/99-gpio.rules
sudo udevadm control --reload-rules && sudo udevadm trigger

🔬 사례 심화 ③: 센서 4형제 한 파일로 정리

실전 규칙

/etc/udev/rules.d/99-robot-sensors.rules

칩 종류가 다르면 제조사ID:제품ID(idVendor:idProduct)만으로 구분 가능합니다.

# CP2102 칩 → LiDAR
SUBSYSTEM=="tty", ATTRS{idVendor}=="10c4", ATTRS{idProduct}=="ea60", SYMLINK+="lidar"
# u-blox 자체 USB → RTK GPS
SUBSYSTEM=="tty", ATTRS{idVendor}=="1546", ATTRS{idProduct}=="01a9", SYMLINK+="rtk_gps"
# CH340 칩 → IMU
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", SYMLINK+="imu"
# 적용 후 — 순서가 어떻게 섞여도 안전
lidar = serial.Serial("/dev/lidar", 115200)
gps   = serial.Serial("/dev/rtk_gps", 38400)

6udev의 한계: 카메라가 그래도 죽는 이유

"udev를 해놔도 다운된다" — 맞는 말입니다. 원인이 두 겹이기 때문입니다.

🏷️

문제 A: 이름이 바뀜

현상video0 → video2 변신
원인재인식 시 순서 변화
결과엉뚱한 장치 열기
✅ udev rule로 해결 가능
🔌

문제 B: 연결 자체가 끊김

현상장치가 순간 사라짐
원인전원 부족·접촉 불량·USB 절전
결과잡고 있던 연결이 죽음
❌ udev만으로 해결 불가

udev는 A를 해결하고, B에서 다시 살아날 발판을 만들어 줍니다. B까지 잡으려면 4종 세트가 필요합니다:

1️⃣

udev 고정 이름

재인식되어도 항상 같은 이름 — /dev/v4l/by-id/ 또는 SYMLINK 규칙

2️⃣

USB 절전 끄기

리눅스가 "안 쓰는 것 같으니 전원 절약" 하며 카메라를 꺼버리는 것 방지 — 이것도 udev rule로!

3️⃣

재연결 로직

프로그램에서 끊김 감지 → by-id 경로로 다시 열기 (try-except + 재시도)

4️⃣

전원 보강

라즈베리파이 다운의 근본 원인 — 공식 27W 어댑터 또는 유전원 USB 허브

2번 상세

특정 장치만 USB 절전 금지하는 udev rule

# Logitech 카메라(제조사ID 046d)는 절대 절전시키지 마라
SUBSYSTEM=="usb", ATTRS{idVendor}=="046d", ATTR{power/autosuspend}="-1"

🎓 종합 정리

udev의 모든 것을 한 장에 담았습니다.

목적명령어

핵심 개념 6가지

1️⃣

udev = userspace /dev

감지는 커널, 이름 정책은 사용자 공간 — devfs 실패에서 배운 설계.

2️⃣

핫플러그가 낳은 해답

2003년, USB 시대의 "순서 기반 이름 혼란"을 끝내려 탄생했다.

3️⃣

부서(서브시스템) 분류

tty·v4l·input·block·net — 직무별 부서가 폴더와 그룹을 결정한다.

4️⃣

그룹이 나뉘는 이유

위험의 성격이 달라서. 모터 열쇠와 카메라 열쇠는 따로 관리한다.

5️⃣

규칙 = 조건 → 행동

SUBSYSTEM 확인 + 신원 확인 → SYMLINK/GROUP/RUN 부여.

6️⃣

udev는 만능이 아니다

이름 문제는 해결, 물리 끊김은 절전 끄기·재연결·전원 보강으로.
