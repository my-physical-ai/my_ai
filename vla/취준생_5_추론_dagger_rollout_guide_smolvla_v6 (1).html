lerobot-rollout &
DAgger 제어 흐름

학습된 정책(Policy)을 로봇에서 실행하고, 실수할 때 사람이 개입해 교정하는 DAgger 방식의 롤아웃 명령어와 키보드 제어 흐름을 정리합니다.
v6 결론 — 기본 DAgger 모드를 쓰고, 저장 키는 Tab이며, 교정을 태스크 완료까지 마무리한 뒤 Tab을 눌러야 온전한 에피소드(동영상)가 저장됩니다.

🚗
이해하기 쉽게!

rollout은 "운전 연수"와 같아요. 학생(정책)이 스스로 운전하다가 위험한 순간이 오면 강사(사람)가 보조 핸들을 잡고 올바른 방향을 잡아주죠. 이때 강사가 개입한 "올바른 조작"이 새 데이터로 기록되어, 다음 학습에서 학생이 더 똑똑해집니다.

💡 실제로는 — 정책이 로봇을 자율 실행(AUTONOMOUS)하다가, 사람이 리더 암(leader arm)으로 개입해 교정(CORRECTING)하면 그 궤적이 데이터셋에 추가됩니다. 이것이 DAgger(Dataset Aggregation)입니다.

🟣 명령어 1 — DAgger 롤아웃 (SmolVLA · top+wrist)

학습된 SmolVLA 정책을 실행하면서, 사람이 교정한 데이터를 새 데이터셋으로 수집하는 DAgger 전략입니다.

rollout_dagger_2realsense.sh 
lerobot-rollout \
  # === 팔로워 로봇 (실제로 움직이는 로봇) ===
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM1 \
  --robot.id=my_follower \
  --robot.cameras="{
      top:   {type: intelrealsense, serial_number_or_name: 138422072965, width: 640, height: 480, fps: 30, warmup_s: 15},
      wrist: {type: opencv,        index_or_path: /dev/wrist_cam,        width: 640, height: 480, fps: 30, fourcc: \"MJPG\"}
  }" \

  # === 학습된 정책 (SmolVLA 체크포인트, 사전학습 파인튜닝) ===
  --policy.path=outputs/train/smolvla_pink_task_v3_dagger_r2/checkpoints/last/pretrained_model \
  --policy.device=cuda \

  # === 카메라 키 이름 매핑 (SmolVLA 필수) ===
  --rename_map='{"observation.images.top":"observation.images.camera1","observation.images.wrist":"observation.images.camera2"}' \

  # === 리더 암 (사람이 개입/교정하는 조종기) ===
  --teleop.type=so101_leader \
  --teleop.port=/dev/ttyACM0 \
  --teleop.id=my_leader \

  # === DAgger 전략 + 데이터 수집 설정 ===
  --strategy.type=dagger \
  --dataset.repo_id=data/rollout_dagger_pink_task_v3_r3 \
  --dataset.single_task="pink block into the box of yellow" \
  --dataset.push_to_hub=false \
  --display_data=false

핵심 파라미터 한눈에 보기

--robot (follower)
실제로 물체를 잡는 팔로워 로봇. 포트 ttyACM1에 연결.
--teleop (leader)
사람이 잡고 교정하는 리더 암. 포트 ttyACM0에 연결.
--strategy.type=dagger
자율 실행 + 사람 교정 데이터를 누적 수집하는 DAgger 모드.
--dataset.repo_id
이번 롤아웃에서 새로 수집되는 교정 데이터 저장 위치. DAgger 데이터셋은 rollout_ 접두사가 붙습니다.
--rename_map
수집 시 카메라 키(top, wrist)를 SmolVLA가 기대하는 camera1, camera2로 매핑. 학습 때와 반드시 동일해야 합니다.
📷
이 명령은 top(RealSense) + wrist(웹캠) 2대 카메라를 사용합니다. top은 시리얼 번호로, wrist는 /dev/wrist_cam udev 심볼릭 링크로 지정합니다. 각 카메라는 640×480 해상도, 30fps로 동작합니다.
⚠️
SmolVLA 핵심 — --rename_map은 학습(train)과 롤아웃(rollout)에서 완전히 똑같이 지정해야 합니다. 키 이름이 하나라도 다르면 정책이 카메라 입력을 찾지 못해 실행이 실패합니다.

🔵 명령어 2 — 기본 롤아웃 (top+wrist · base 전략)

RealSense(top) + 웹캠(wrist)을 사용하고, 데이터 수집 없이 SmolVLA 정책 성능만 확인하는 base 전략입니다.

  # === 학습된 정책 (SmolVLA 체크포인트) ===

  # === 리더 암 ===

💡
top 카메라는 RealSense(warmup_s: 15로 15초 예열)이고, wrist 카메라는 OpenCV 웹캠(/dev/wrist_cam, MJPG 코덱)입니다. MJPG 코덱은 USB 대역폭을 아껴 프레임 드롭을 막습니다.

🟢 명령어 3 — DAgger 롤아웃 (3회 반복 자동 종료)

명령어 1과 같은 DAgger 수집이지만, --strategy.num_episodes=3으로 에피소드 3회를 채우면 자동으로 종료됩니다. 짧은 수업 실습이나 라운드별 소량 수집에 적합합니다.

rollout_dagger_3episodes.sh 
lerobot-rollout \
  # === 팔로워 로봇 (실제로 움직이는 로봇) ===
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM1 \
  --robot.id=my_follower \
  --robot.cameras="{
      top:   {type: intelrealsense, serial_number_or_name: 138422072965, width: 640, height: 480, fps: 30, warmup_s: 15},
      wrist: {type: opencv,        index_or_path: /dev/wrist_cam,        width: 640, height: 480, fps: 30, fourcc: \"MJPG\"}
  }" \

  # === 학습된 정책 (SmolVLA 체크포인트) ===
  --policy.path=outputs/train/smolvla_pink_task_v3_dagger_r2/checkpoints/last/pretrained_model \
  --policy.device=cuda \

  # === 카메라 키 이름 매핑 (SmolVLA 필수) ===
  --rename_map='{"observation.images.top":"observation.images.camera1","observation.images.wrist":"observation.images.camera2"}' \

  # === 리더 암 (사람이 개입/교정하는 조종기) ===
  --teleop.type=so101_leader \
  --teleop.port=/dev/ttyACM0 \
  --teleop.id=my_leader \

  # === DAgger 전략 + 반복 3회 지정 ===
  --strategy.type=dagger \
  --strategy.num_episodes=3 \
  --dataset.repo_id=data/rollout_dagger_pink_task_v3_r3 \
  --dataset.single_task="pink block into the box of yellow" \
  --dataset.push_to_hub=false \
  --display_data=false

명령어 1과의 차이는 단 한 줄

--strategy.num_episodes=3
에피소드 3회를 채우면 롤아웃이 자동 종료됩니다. 숫자만 바꾸면 5회, 10회, 20회 등 원하는 반복 횟수로 조절할 수 있습니다.
에피소드 카운트 기준
기본 모드(corrections-only)에서는 교정(개입) 1회 = 1 에피소드로 집계됩니다. 즉 사람이 3번 교정하면 종료됩니다.
💡
수업 활용: 횟수를 지정하지 않으면 사람이 직접 종료(Esc)할 때까지 계속 돕니다. 실습 시간이 정해진 수업에서는 num_episodes로 팀당 수집량을 통일하면 공정한 비교와 시간 관리가 쉬워집니다.

🛠️ SmolVLA 롤아웃 전 필수 준비

SmolVLA는 롤아웃 전에 두 값을 확인해야 합니다 — chunk_size = 50(예측)과 n_action_steps = 50(실행). 이름이 비슷해 헷갈리지만 서로 다른 값이고, 맞춰야 하는 이유도 다릅니다.

⚙️
이해하기 쉽게!

SmolVLA는 한 번에 동작 50개(청크 50)를 계획해요. 학습 때는 이 값이 작게 저장돼 있을 수 있어서, 롤아웃 전에 실행할 동작 수를 50으로 맞춰줘야 매끄럽게 움직입니다. 마치 자동차 시동 전에 좌석과 거울을 맞추는 것과 같아요.

💡 실제로는 — 모든 체크포인트의 config.json에서 n_action_steps를 50으로 바꿔야 합니다. sed 한 줄로 처리합니다.

patch_n_action_steps.sh 
# 체크포인트 폴더의 모든 config.json에서 n_action_steps를 50으로 패치
find outputs/train/smolvla_pink_task_v3_dagger_r2/checkpoints \
  -name "config.json" \
  -exec sed -i 's/"n_action_steps": [0-9]*/"n_action_steps": 50/' {} +
⚠️
이 패치를 빠뜨리면 로봇이 짧게 끊기거나 덜덜거리며 움직일 수 있습니다. 롤아웃 명령을 실행하기 전에 반드시 한 번 수행하세요.

🎯 두 값은 다릅니다 — chunk_size vs n_action_steps

이름이 비슷해 하나로 착각하기 쉽지만, 하나는 "몇 개를 내다볼까(예측)", 다른 하나는 "그중 몇 개를 실행할까(실행)"입니다. 관계는 항상 n_action_steps ≤ chunk_size입니다.

🗺️
이해하기 쉽게!

내비게이션이 앞으로 50km 경로를 미리 계산해두는 게 chunk_size=50이에요. 하지만 실제로는 그 경로를 따라 50km를 다 달린 뒤 다시 경로를 새로 계산하죠 — 이게 n_action_steps=50입니다. 만약 n_action_steps=1이면, 1km 갈 때마다 50km 경로 전체를 매번 새로 계산하는 셈이라 차가 자꾸 멈칫거립니다.

chunk_size = 50  (예측)
정책이 한 번에 예측하는 동작 시퀀스의 길이. SmolVLA는 미래 50스텝을 한 묶음으로 내놓도록 학습됐습니다. 이건 모델 출력 헤드의 텐서 크기에 박힌 구조값입니다.
n_action_steps = 50  (실행)
예측한 50개 중 실제로 실행하고 다음 추론까지 갈 개수. 체크포인트 기본값이 1로 잘못 박혀 있어, 롤아웃 전 반드시 50으로 고쳐야 합니다.

왜 chunk_size = 50이어야 하나 — 학습과 같아야 하니까

🔒
chunk_size는 바꾸는 값이 아니라 학습값을 그대로 따라가는 값입니다. 학습된 가중치는 "50개 출력"에 맞춰져 있어서, 추론 때 다른 값을 주면 ① 텐서 shape가 안 맞아 에러가 나거나, ② 형상이 맞아도 "50스텝 앞을 내다보는 습관"으로 학습된 예측 분포가 무너집니다. 학습·추론 조건은 같아야 한다는 ML의 기본 원칙 — SmolVLA는 그 값이 50입니다.

왜 n_action_steps = 50이어야 하나 — 기본값 1이 함정이라서

🕳️
SmolVLA 체크포인트의 config.json에는 이 값이 1로 기본 설정돼 있습니다. 이대로 두면 정책이 50개를 힘들게 예측해놓고 딱 1개만 실행한 뒤 버리고, 매 스텝마다 무거운 VLA 추론을 새로 돌립니다. SmolVLA는 추론이 느린 모델이라 한 스텝 움직이고 멈칫, 또 멈칫하는 극심한 버벅임이 생기고, 예측의 49/50을 매번 버리니 계산 낭비도 큽니다. 50으로 바꾸면 추론 횟수가 1/50로 줄어 매끄러워집니다.

한눈에 — 예측 vs 실행

예측 (chunk_size)
50개 예측 →
… (총 50)
실행 =50 (권장)
… 50개 모두 실행 → 추론 1회 / 50스텝 ✅
실행 =1 (기본·함정)
1개만 실행, 49개 버림 → 추론 50회 / 50스텝 ❌ 버벅임

패치 전 확인 — 지금 값이 뭔지 먼저 보기

check_action_params.sh 
# 롤아웃 전, 두 값이 실제로 어떻게 박혀 있는지 확인
grep -E '"(chunk_size|n_action_steps)"' \
  outputs/train/smolvla_pink_task_v3_dagger_r2/checkpoints/last/pretrained_model/config.json

# 예상 출력:
#   "chunk_size": 50,        ← 학습값 그대로 (건드리지 않음)
#   "n_action_steps": 1,     ← ★ 1이면 함정! 50으로 패치 필요
🧭
정리: chunk_size는 "학습과 같아야 해서" 50 — 그래서 확인만 하고 손대지 않습니다. n_action_steps는 "기본값 1이 함정이라서" 50으로 패치합니다. 이유가 서로 달라서, 하나는 확인·하나는 수정이라는 점을 꼭 기억하세요.
🎛️
DAgger 교정 팁: n_action_steps=50이면 정책이 한 번에 약 1.6초(50스텝 @30fps)를 쭉 실행합니다. 교정 실습에서 개입 반응이 둔하게 느껴지면, 25~30 정도로 낮춰 정책이 더 자주 관측을 갱신하게 할 수 있습니다. (단, chunk_size는 절대 낮추지 마세요 — 학습값이라 예측 품질이 깨집니다.)

🎮 DAgger 키보드 제어 흐름

롤아웃 중에는 Space와 Tab 두 키로 3가지 상태를 오갑니다. 핵심 규칙: 먼저 Space로 일시정지한 뒤에야 Tab으로 교정할 수 있습니다.

🚦
핵심 규칙

달리는 차(AUTONOMOUS)에서 바로 핸들을 뺏을 수는 없습니다. 먼저 Space로 차를 세우고(PAUSED), 그 다음 Tab으로 핸들을 넘겨받아야(CORRECTING) 합니다.

상태 전이 다이어그램

AUTONOMOUS
정책이 로봇을 자율 실행 중
↓ ⎵ Space 정책 일시정지 ↓
PAUSED
로봇 정지 · 교정 대기 상태
↓ ⇥ Tab 리더 암으로 교정 시작 ↓
CORRECTING
사람이 리더 암으로 직접 조작 · 교정 데이터 기록
↑↓ ⇥ Tab 교정 종료 → 다시 PAUSED로 ↑
🔁
PAUSED에서 Space를 다시 누르면 AUTONOMOUS로 복귀해 정책이 이어서 실행됩니다. 즉 Space는 "정책 재생/정지" 토글, Tab은 "사람 교정 시작/종료" 토글로 이해하면 쉽습니다.

실전 조작 순서 (4단계)

Space — 정책 일시정지
AUTONOMOUS → PAUSED   로봇이 실수하려는 순간, Space로 정책을 멈춥니다.
Tab — 교정 시작
PAUSED → CORRECTING   리더 암을 잡고 올바른 동작을 직접 시연합니다. 이 궤적이 데이터로 기록됩니다.
Tab — 교정 종료
CORRECTING → PAUSED   교정을 마치면 Tab을 다시 눌러 정지 상태로 돌아옵니다.
Space — 정책 재개
PAUSED → AUTONOMOUS   다시 Space를 눌러 정책이 이어서 자율 실행하도록 합니다.
⚠️
주의: AUTONOMOUS 상태에서 곧바로 Tab을 눌러도 교정으로 넘어가지 않습니다. 반드시 Space → PAUSED를 먼저 거쳐야 합니다.

🏁 v6 실무 결론 — 기본 DAgger로, 교정을 끝까지 가야 저장된다

소스(dagger.py·configs.py)를 직접 확인해 확정한 현재 v0.6.0 기준 최선의 방식입니다. 결론부터: 기본 DAgger 모드(record_autonomous 없이)를 쓰고, 저장 키는 Tab이며, 교정을 시작했으면 태스크 완료까지 손 떼지 말고 마무리한 뒤 Tab을 눌러야 온전한 에피소드(동영상)가 저장됩니다.

🎬
이해하기 쉽게!

녹화 버튼(Tab)을 누른 순간부터 다시 누를 때까지가 한 편의 영상입니다. 중간에 "여기까지 교정했으니 됐다" 하고 완료 전에 Tab을 누르면, 영상이 결말 없이 뚝 끊긴 채 저장됩니다. 그래서 블록을 박스에 넣는 마지막 순간까지 손으로 끌고 간 다음 Tab을 눌러야 "실패 → 회복 → 완료"가 담긴 제대로 된 한 편이 남습니다.

💡 실제로는 — dagger.py에서 교정 종료(Tab) = save_episode() 호출입니다. 즉 Tab을 누르는 그 지점까지의 궤적이 그대로 하나의 에피소드로 확정·저장됩니다.

🎹 실제 키는 3개뿐 — 소스로 확정

DAggerKeyboardConfig 기본값입니다. 실행 직후 터미널에도 pause_resume='space', correction='tab', ... 로 출력됩니다.

Space · pause_resume
정책 실행 토글. AUTONOMOUS ↔ PAUSED. 실수 조짐이 보이면 먼저 Space로 멈춥니다.
Tab · correction = 저장
교정 녹화 토글. PAUSED ↔ CORRECTING. 교정을 끝내는 Tab이 곧 저장입니다("Correction N saved" 음성).
Enter · upload / ESC · 종료
Enter는 Hub 푸시(push_to_hub=false면 미사용). ESC는 세션 전체 종료.
🚫
재녹화(다시 찍기) 키는 없습니다. discard/re-record 기능은 episodic 전략에만 있고 기본 DAgger엔 코드 자체가 없습니다. 그래서 "Tab 누르기 전에 완료까지 제대로 끝내는 것"이 유일한 품질 관리 수단입니다. 이미 저장된 나쁜 에피소드는 나중에 lerobot-edit-dataset로 해당 episode_index를 삭제해 정리합니다.

✅ 왜 이게 "지금 가장 좋은 솔루션"인가

① 학습에 유효한 온전한 궤적
"실패 상태 → 올바른 완료 행동"의 매핑이 끝까지 담겨야, 원본 데모와 합쳐 파인튜닝할 때 일관된 신호가 됩니다. 중간에 끊기면 완료로 가는 뒷부분이 사라집니다.
② 초반 개입의 이점
되돌릴 수 없는 실수·머뭇거림·궤적 이탈은 대개 초반 접근·정렬에서 나타납니다. 이때 한 번 바로잡아 완료까지 끌고 가면 가장 값어치 큰 데이터가 됩니다.
③ 개입은 최소·결정적으로
한 에피소드에 개입이 여러 번 흩어지면 데이터가 지저분해집니다. 초반 한 번, 결정적일 때만 개입하고 이후엔 완료까지 이어가는 게 품질·효율 모두 낫습니다.
④ intervention 태그 유지
교정 프레임엔 intervention=True가 붙어(dagger.py), 나중에 개입 프레임에 가중치를 더 주는 학습이 가능합니다.

🆕 v5 핵심 — --strategy.record_autonomous=true

운전 연수를 "강사가 핸들 잡은 순간만" 녹화하면(기본 모드), 나중에 영상만 봐서는 "학생이 어쩌다 그 위험한 상황에 빠졌는지"를 알 수 없습니다. record_autonomous=true는 연수 전 과정을 통째로 녹화하는 것 — 학생의 실수 과정 + 강사의 교정이 한 편의 영상으로 남습니다.

✅ 이 옵션의 장점 4가지

① 실패 맥락 보존
정책이 어쩌다 잘못된 상태에 빠졌는지 그 과정이 통째로 남습니다. 교정만 저장하면 "왜 그 상황이 됐는지"가 사라져, 다단계 작업의 분포 이동(distribution shift)을 못 배웁니다.
② 다단계 작업에 필수
집기 → 넣기처럼 단계가 이어지는 작업은, 1단계 자율 실행의 결과가 2단계 시작 상태를 결정합니다. 자율 구간이 있어야 단계 간 연결을 학습합니다.
③ 성공·실패 균형
정책이 잘한 자율 구간도 함께 저장돼, 교정 데이터에만 과적합되는 것을 막습니다. "정상 행동"의 분포가 유지됩니다.
④ intervention 플래그로 취사선택
전체를 저장하되 intervention=True 태그가 붙으므로, 학습 때 개입 프레임에만 가중치를 더 줄 수 있습니다. 저장은 전체, 강조는 교정 — 둘 다 챙깁니다.
🎯
왜 2단계라서 이걸 써야 하나? — 지금 작업이 "핑크 블록 집기 → 노란 박스에 넣기"의 2단계 연쇄라, 1단계에서 정책이 어떻게 집었는지(자율 구간)가 2단계 성패를 좌우합니다. 교정만 저장하면 이 단계 간 인과가 끊겨 난이도 높은 작업이 잘 학습되지 않습니다. 소량·단순 작업이면 기본 모드가 효율적이지만, 고난도 다단계에서는 전체 저장이 정석입니다.

# 사용법: python check_dagger_dataset.py data/rollout_dagger_pink_task_v3_r3_full
import sys, glob
import pandas as pd

root = sys.argv[1] if len(sys.argv) > 1 else "data/rollout_dagger_pink_task_v3_r3_full"
files = sorted(glob.glob(f"{root}/data/**/*.parquet", recursive=True))

# ① 안전판: 파일이 없으면 친절히 알려주고 종료
if not files:
    print(f"❌ parquet 파일이 없습니다: {root}/data/")
    print("   경로가 맞는지, 수집이 끝났는지 확인하세요.")
    sys.exit(1)

print(f"✅ parquet 파일 {len(files)}개 발견")

# ② 전체 에피소드를 합쳐 컬럼·개입 비율 확인
df = pd.concat([pd.read_parquet(f) for f in files], ignore_index=True)
print("컬럼:", df.columns.tolist())
print("전체 프레임 수:", len(df))

# ③ 핵심: intervention 태그 존재 여부 + 비율
if "intervention" in df.columns:
    n_iv = int(df["intervention"].sum())
    ratio = n_iv / len(df) * 100
    print(f"🖐  개입 프레임: {n_iv} / {len(df)} ({ratio:.1f}%)")
    if ratio == 0:
        print("⚠️  개입이 0% — 교정이 저장되지 않았습니다. 키 조작을 확인하세요.")
    elif ratio > 80:
        print("⚠️  개입 80%↑ — corrections-only 모드일 가능성. 자율 구간이 거의 없습니다.")
    else:
        print("👍  자율+교정이 함께 저장된 정상적인 전체 저장 데이터로 보입니다.")
else:
    print("ℹ️  intervention 컬럼 없음 — 이 LeRobot 버전/설정에서는 태그를 남기지 않습니다.")

# ④ 에피소드 개수도 확인 (있으면)
if "episode_index" in df.columns:
    print("에피소드 수:", df["episode_index"].nunique())

⚡ 비동기 추론 (Async Inference) — SmolVLA의 핵심

SmolVLA 같은 큰 VLA 모델은 추론이 느려서, 로봇이 "다음 동작 계산될 때까지 멈춰 기다리는" 지연이 생깁니다. 비동기 추론은 동작 예측과 동작 실행을 분리해 이 멈춤을 없앱니다.

🍳
이해하기 쉽게!

동기 추론은 요리사가 접시 하나를 다 내주고 나서야 다음 요리를 시작하는 것과 같아요. 손님(로봇)은 그동안 가만히 기다립니다. 비동기 추론은 손님이 지금 접시를 먹는 동안 요리사가 미리 다음 접시를 만드는 것이라, 접시가 끊기지 않아요.

💡 실제로는 — 로봇이 현재 동작 청크를 실행하는 동안, 정책 서버는 이미 다음 청크를 계산합니다. 현재 청크가 소진되기 전에 다음 청크가 준비되므로 멈춤(idle)이 사라집니다.

🅰️ 방법 1 — 내장 비동기 백엔드 (--inference.type=rtc) · 수업 권장

별도 서버 없이, 앞의 명령어 1·2·3에 플래그만 추가하면 됩니다. 모든 전략(base·dagger)과 호환됩니다. 메인 루프가 현재 동작을 실행하는 동안 백그라운드 스레드가 다음 청크를 병렬 계산합니다.

  --inference.type=rtc \

  --inference.rtc.max_guidance_weight=10.0 \

  --policy.path=/home/zetabank/lerobot_outputs/train/smolvla_pink_task_2cam/checkpoints/last/pretrained_model \

  --rename_map="{observation.images.top: observation.images.camera1, observation.images.wrist: observation.images.camera2}" \

  --duration=60 \
  --display_data=false

블렌딩 스케줄: LINEAR · EXP · ONES · ZEROS. 기본값으로 시작하세요. (아래 그림 설명 참고)

🏃 prefix_attention_schedule 쉽게 이해하기 — 이어달리기 바통 터치

🏃
이해하기 쉽게!

로봇은 동작을 "청크(계획 묶음)" 단위로 실행합니다. 옛 청크가 달리는 선수, 새 청크가 다음 선수예요. 문제는 바통을 넘기는 순간 — 두 선수의 속도가 다르면 바통을 떨어뜨리죠(= 팔이 "툭" 튀는 현상). 그래서 RTC는 바통 터치 구간에서 옛 계획과 새 계획을 겹쳐서 섞는데, 이 스케줄은 그 구간에서 "옛 계획을 얼마나, 어떤 식으로 존중할까"를 정하는 규칙입니다.

💡 기억법 — execution_horizon이 바통 터치 구간의 "길이"라면, prefix_attention_schedule은 그 구간 안에서 섞는 "모양"입니다.

📉 블렌딩 구간에서 "옛 계획의 비중"이 줄어드는 4가지 모양
가로: 블렌딩 구간 진행 (execution_horizon 스텝) · 세로: 옛 계획을 존중하는 비중
ONES
앞 곡 볼륨 끝까지 크게 → 가장 부드러움, 반응 느림
LINEAR
일정하게 서서히 줄임 → 균형형 (무난)
EXP
처음에 확 줄이고 뒤엔 살짝 → 새 계획 빠른 반영
ZEROS
앞 곡 뚝 끊기 → 블렌딩 없음, 튐 위험 최대
🎚️
튜닝 요령: 먼저 기본값으로 돌려보세요(정책마다 잘 맞는 스케줄이 이미 지정돼 있음). 그다음 로봇 팔이 청크 경계에서 움찔거리면 → ONES 쪽으로, 새 상황 반응이 굼뜨면 → EXP 쪽으로 조정합니다. ZEROS는 사실상 "블렌딩 끄기"라 실습에서는 비교 실험용으로만 쓰세요.
🎮
DAgger와도 호환: 공식 문서 기준 "모든 전략이 두 백엔드 모두와 작동"하므로, 명령어 1(dagger)에도 --inference.type=rtc를 붙일 수 있습니다. 단, 앞서 본 교정 후 재개 시 스냅백 이슈(GitHub #3747)가 바로 RTC+DAgger 조합에서 보고된 것이니, 재개 직후 1~2초는 거동을 관찰하세요.

🅱️ 방법 2 — 분산 비동기 (정책 서버 + 로봇 클라이언트)

추론을 다른 PC(원격 GPU)에서 돌리고 싶을 때 사용합니다. 로봇 옆 PC가 약할 때 유용합니다.

📦 0단계 — 설치 (async 의존성)

🧠 1단계 — 정책 서버 켜기 (터미널 1 · GPU PC)

policy_server.sh 
python -m lerobot.async_inference.policy_server \
  --host=0.0.0.0 \   # 같은 PC면 127.0.0.1, 원격이면 0.0.0.0
  --port=8080
💡
서버는 처음엔 빈 껍데기입니다. 어떤 정책을 쓸지는 클라이언트가 처음 연결할 때(handshake) 전달합니다. 그래서 서버 명령엔 --host와 --port만 있으면 됩니다. 원격 PC로 돌릴 때는 0.0.0.0으로 열고, 클라이언트에는 서버의 실제 IP를 알려주세요.

🤖 2단계 — 로봇 클라이언트 켜기 (터미널 2 · 로봇 PC)

robot_client_smolvla.sh 
python -m lerobot.async_inference.robot_client \
  # === 서버 주소 (1단계에서 켠 서버) ===
  --server_address=127.0.0.1:8080 \   # 원격이면 서버_IP:8080

  # === 로봇 (팔로워) ===
  --robot.type=so101_follower \
  --robot.port=/dev/ttyACM1 \
  --robot.id=my_follower \
  --robot.cameras="{ top: {type: intelrealsense, serial_number_or_name: 116622071569, width: 640, height: 480, fps: 30}, wrist: {type: opencv, index_or_path: 12, width: 640, height: 480, fps: 30}}" \

  # === 정책 (SmolVLA · 서버에서 로드됨) ===
  --task="pink block into the box of yellow" \
  --policy_type=smolvla \
  --pretrained_name_or_path=outputs/train/smolvla_pink_task_2cam/checkpoints/last/pretrained_model \
  --policy_device=cuda \

  # === 비동기 핵심 튜닝 파라미터 ===
  --actions_per_chunk=50 \
  --chunk_size_threshold=0.5 \
  --aggregate_fn_name=weighted_average \
  --debug_visualize_queue_size=true
📷
카메라 키 주의: 클라이언트의 카메라 키는 정책이 기대하는 이름과 일치해야 합니다. 학습 때 rename_map으로 camera1/camera2를 썼다면, 여기서도 동일하게 맞추세요. (앞선 롤아웃 명령어와 같은 원칙 — 학습·추론 간 키 일관성)

🎛️ 핵심 튜닝 파라미터 2가지

파라미터기본값하는 일
actions_per_chunk 50 정책이 한 번에 내놓는 동작 개수. 클수록 큐가 빌 위험은 줄지만, 먼 미래까지 예측해 정밀도가 떨어질 수 있음. 보통 10~50.
chunk_size_threshold 0.5 큐가 이 비율 이하로 줄면 새 관측값을 서버로 보냄(0~1). 클수록 자주 갱신돼 반응성↑·대역폭↑. 0에 가까우면 동기 추론처럼 됨.
actions_per_chunk ↑
작게 → 정밀하지만 큐 빌 위험 크게 → 안정적이나 정밀도 ↓
chunk_size_threshold ↑
0에 가까이 → 동기(느림) 1에 가까이 → 반응성↑·대역폭↑
📊
튜닝 3원칙: ① 큐가 자주 비면 fps를 낮추세요(서버 추론이 못 따라오는 것). ② chunk_size_threshold는 0.5~0.6이 대체로 잘 맞습니다. ③ --debug_visualize_queue_size=true로 큐 크기 그래프를 보면서 조정하세요 — 큐가 0에 자주 닿으면 멈춤이 생기는 신호입니다.
🧮
서버 메모리 참고: 추론 시 π0는 약 14GB, SmolVLA는 약 2GB를 씁니다. SmolVLA가 가벼워서 작은 GPU에서도 async가 잘 돕니다. 정책·디바이스 조합이 평균 추론 지연을 좌우합니다.

✅ 한 줄 요약

🎯

rollout으로 정책을 실행하고, 실수할 때 Space(정지) → Tab(교정) → Tab(교정끝) → Space(재개) 순서로 사람이 개입해 더 나은 데이터를 계속 쌓는 것 — 이것이 DAgger의 핵심입니다.

🏁 v6 확정 방침 — 기본 DAgger 모드(record_autonomous 없이)를 씁니다. Tab이 저장 키이고, 교정을 태스크 완료까지 마무리한 뒤 Tab을 눌러야 "실패→회복→완료"가 담긴 온전한 에피소드(동영상)가 저장됩니다. 재녹화 키는 없으니(episodic 전용), 나쁜 에피소드는 lerobot-edit-dataset로 사후 삭제합니다.

🆕 참고(v5) — "집기→넣기" 자율 구간 인과까지 통째로 담고 싶을 때만 --strategy.record_autonomous=true(전체 저장)를 검토합니다. 수집 후 check_dagger_dataset.py로 intervention 태그·개입 비율(~30%)을 검증하고, 기존 수집분과 합쳐 재학습하세요.
